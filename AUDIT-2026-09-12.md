# Audit WilayaDZ — 12 septembre 2026

État historique avant corrections. Voir [la fiabilisation](CORRECTIONS-2026-09-12.md) pour le traitement des défauts.

Version examinée : `c857a3b`. Site : https://wilayadz.smnc.win/.

L'application fonctionne sur les parcours courants examinés, mais plusieurs défauts concernent la fiabilité de la progression et des transferts. **La priorité est la clé Android exposée, puis la synchronisation.** Ces corrections peuvent se faire en conservant l'interface actuelle.

Cet audit n'a changé ni le code de l'application ni la progression du compte réel et n'a déclenché aucun déploiement. Les scénarios qui écrivent des données ont utilisé des comptes fictifs, une base SQLite jetable et un serveur de courriels simulé.

## Défauts relevés

### 1. P1 — Clé de signature Android exposée

**Confirmé dans le dépôt public GitHub**, consulté pendant l'audit : `android/keystore/wilayas-v2.jks` est accessible et `PROJECT_NOTES.md:142` contient son mot de passe. Les notes indiquent que cette clé signe les versions distribuées depuis la v9. Le secret n'est pas reproduit ici.

Conséquence : un tiers disposant de ces fichiers peut signer un APK avec cette identité. Cela ne prouve pas qu'une attaque a eu lieu, et ne permet pas à lui seul de modifier le site web.

Action : traiter cette clé comme compromise, préparer la migration de signature compatible avec les installations existantes, sortir les secrets du dépôt et nettoyer l'historique. Supprimer uniquement la ligne actuelle ne rendrait pas la clé secrète à nouveau. Ne pas remplacer aveuglément la clé au risque de bloquer les mises à jour Android.

### 2. P1 — Des données synchronisées sont écrasées par l'état local

**Reproduit avec les fonctions réelles du client**, transport HTTP simulé : le compte distant contient 900 XP et la Clé acquise ; le client reçoit ces valeurs dans `p.data`, mais `state.xp` reste à 0 et `state.keyDone` reste faux. Le prochain `persist()` remet les XP locaux à 0.

Deux causes : `changed` ne compte que les wilayas ajoutées/améliorées ; et la synchronisation silencieuse ne recharge jamais l'état actif. Les champs XP, record Rafale, Clé et certaines mises à jour de série peuvent diverger. Les objets progression/couronnes sont en partie partagés par référence et ne suivent pas exactement le même comportement.

Source : `app/p4k_cloud.js:155`, `app/p4k_cloud.js:194`, `app/p4g_account.js:117` et `app/p4g_account.js:228`.

Action : réconcilier les données fusionnées avec l'état actif sans interrompre une leçon, et détecter les changements sur tous les champs concernés. Tester deux appareils, y compris quand seuls les XP ou la Clé changent. Le test démontre l'écrasement local ; il ne démontre pas une suppression définitive des 900 XP sur le serveur.

### 3. P1 — La synchronisation annule les baisses de maîtrise après une erreur

**Reproduit** : état local descendu à la boîte 3, sauvegarde distante encore en boîte 5 ; après synchronisation, la boîte locale revient à 5 et retrouve l'ancienne échéance.

`recordAnswer()` fait volontairement redescendre une erreur de deux niveaux, mais `mergeInto()` conserve toujours le niveau le plus élevé. La synchronisation efface donc une information pédagogique récente : cette wilaya devrait être revue plus tôt.

Source : `app/p4a_core.js:114`, `app/p4g_account.js:213`.

Action : dater les mises à jour par wilaya ou synchroniser les événements de réponse. Distinguer une réponse récente d'une meilleure valeur historique.

### 4. P2 — « Réinitialiser la progression » ne réinitialise pas la mémoire distante

**Reproduit sur données fictives** : après remise à zéro locale, la synchronisation réimporte une couronne à 5, une wilaya en boîte 5 et les anciens XP dans le profil. Le message « Progression réinitialisée » laisse croire à une opération durable.

Source : `app/p4e_practice.js:129`, `app/p4g_account.js:207`.

Action : définir une réinitialisation explicite du compte avec une version de remise à zéro commune aux appareils. Tester qu'un second appareil ne ressuscite pas les anciennes données. Cette opération doit rester distincte d'une fusion ordinaire.

### 5. P2 — Les transferts acceptent des structures invalides

**Reproduit dans un contexte JavaScript isolé** : une entrée de progression `null` provoque une exception à la fusion. Une clé spéciale `__proto__` modifie le prototype des objets dans ce contexte. Le contrôle de format ne valide ni les codes de wilaya ni la structure des valeurs ; le serveur ne fait lui aussi qu'un contrôle très superficiel du contenu.

L'import manuel demande une confirmation, mais un checksum valide ne garantit pas un contenu sain. Aucune prise de contrôle de compte ni exécution de script injecté n'a été démontrée ici.

Source : `app/p4g_account.js:191`, `app/p4g_account.js:213`, `app/p4g_account.js:238`, `app/p4h_profileui.js:820`, `server/app.py:454`.

Action : valider intégralement le schéma des transferts et des sauvegardes : codes autorisés, tableaux, bornes numériques, couronnes, confusions, avatar. Rejeter les clés spéciales et utiliser des dictionnaires sans prototype lorsque pertinent. Afficher une erreur d'import récupérable.

### 6. P2 — Le QR de transfert devient inutilisable avec une photo

**Reproduit dans le navigateur local en HTTP** avec une image JPEG artificielle de 160 × 160 : code de transfert de 22 863 caractères, aucun SVG QR produit, message « Code QR indisponible sur cet appareil. »

L'avatar est embarqué dans le code, puis dans l'URL du QR. La capacité du QR est dépassée ; le problème n'est pas l'appareil. Un test direct de la bibliothèque accepte une chaîne de 500 caractères et rejette celle de 6 000.

Source : `app/p4g_account.js:181`, `app/p4h_profileui.js:853`, `app/p4h_profileui.js:896`.

Action : proposer un transfert compact sans photo, ou un mécanisme de lien court approprié. Prévenir clairement quand le QR ne peut pas contenir la sauvegarde et proposer l'export fichier. Ne pas envoyer silencieusement la photo à un nouveau service.

### 7. P2 — Chlef porte deux noms arabes différents selon l'écran

**Observé sur le site connecté** : la carte indique « Chlef — الشلف », tandis que le registre indique « Chlef — الأصنام ». Le dictionnaire général contient l'ancien nom, repris également par les exercices.

Source : `app/p4a_core.js:10`, `app/p4f_i18n.js:72`, `app/p4r_map.js:14`.

Action : utiliser الشلف comme nom actuel dans le registre et les exercices ; garder الأصنام comme nom historique explicitement présenté dans l'explication du classement de 1974. Une seule donnée de référence doit alimenter les écrans courants.

### 8. P2 — Infos affirme qu'il n'y a pas de compte en ligne

**Observé sur le site connecté** : la section Profil & synchronisation dit « il n'y a pas de serveur, donc pas de compte en ligne », alors que le compte est obligatoire et la synchronisation automatique existe.

Source : `app/p3_body.html:165`.

Action : expliquer le fonctionnement actuel : première connexion en ligne, apprentissage possible hors connexion ensuite, synchronisation au retour du réseau et transfert manuel facultatif. Retirer aussi la promesse absolue « sans jamais rien perdre » tant que les défauts ci-dessus existent.

### 9. P3 — L'avertissement sur les codes 59–69 est dépassé

**Vérification documentaire** : l'ordre utilisé par l'application correspond à la liste 59–69 publiée dans le [Journal officiel n° 26 du 9 avril 2026, annexe 1, page 6](https://www.joradp.dz/FTP/jo-francais/2026/F2026026.pdf). Les textes de l'application présentent pourtant encore cet ordre comme fondé seulement sur la presse et à confirmer.

Source : `app/p3_body.html:159`, `app/p3_body.html:239`.

Action : actualiser les références et distinguer l'annonce de 2025 de la formalisation de 2026. Cette vérification porte sur les noms et l'ordre ; elle ne certifie pas les frontières géographiques des 69 tracés communautaires.

### 10. P2 — Chaque publication programme une interruption de l'API de production

**Confirmé dans le workflow** : après le déploiement, il exécute `docker stop wilaya-api`, redémarre le serveur web, attend au moins cinq secondes, puis redémarre l'API. Le test de résistance est donc effectué sur les conteneurs qui servent réellement l'application.

Conséquence attendue : connexions et synchronisations indisponibles pendant cette fenêtre ; une interruption du job avant le redémarrage peut prolonger la panne. L'audit n'a pas provoqué cet arrêt pour le mesurer.

Source : `.github/workflows/deploy.yml:62`.

Action : effectuer ce test sur des conteneurs d'essai isolés. Conserver seulement les contrôles de santé non perturbateurs après publication ; garantir la remise en service dans les tests d'arrêt.

### 11. P2 — Plusieurs tests peuvent terminer « au vert » sans vérifier leur objectif

**Observé pendant l'audit** : `test_ladder.js` écrit « bonne option introuvable, test sauté » puis sort avec le code 0. Les anciens tests `test_life.js` et `test_rig.js` impriment respectivement zéro micro-geste et une indépendance des calques fausse, sans échouer. Ils ne constituent donc pas une preuve de validation de ces animations actuelles. Le test Rive récent, lui, passe ses assertions.

Source : `tests/test_ladder.js:62`, `tests/test_life.js:53`, `tests/test_rig.js:49`. Le workflow de publication ne lance actuellement que les tests Python du service de comptes, pas les tests navigateur.

Action : rendre les scénarios déterministes, échouer lorsqu'une vérification attendue n'a pas eu lieu, retirer ou adapter les tests devenus obsolètes et ajouter les régressions de synchronisation à la validation avant publication.

## Limites et ordre conseillé

Ce relevé couvre les grands parcours web, le code du client/serveur et la configuration de publication. Il ne certifie pas l'absence de tout autre bug. Pas de validation sur téléphone physique, Safari iOS, APK installé, délivrabilité réelle des courriels, charge simultanée, restauration des sauvegardes serveur ou exactitude géographique exhaustive. L'accès Google réel n'a pas été rejoué ; la couverture automatisée ne remplace pas ce contrôle fournisseur.

Ordre proposé : sécuriser la signature Android ; corriger la synchronisation et la réinitialisation ; durcir les transferts et réparer le QR ; harmoniser les données et textes ; améliorer les contrôles avant publication. Conserver les composants, couleurs, mascottes et disposition existants pour ces corrections.
